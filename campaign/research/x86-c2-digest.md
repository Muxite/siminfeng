# Digest of x86 D041-D048 for the Jetson over-memory lane (2026-11-10)
Source: `origin/x86/c2-resume` (`START-HERE.md` section 0, `decisions/D041..D048`). x86 hardware is an RTX 5070 Ti (16 GB VRAM, discrete, PCIe 4.0) plus a Ryzen 7 3700X, models Qwen3-30B-A3B Q4_K_M and Qwen3.6-35B-A3B. Do not pool t/s across hosts.
Jetson context: Qwen3.6-35B-A3B UD-Q4_K_XL (22.4 GB) on 7.4 GiB shared DRAM, ~570 MiB/s NVMe, `-lm mmap -ngl 99 -cmoe`, decode 1.2-1.36 t/s, disk-bound: decode ~ disk_BW / (615 MB x miss_rate); page-cache LRU hit ~62% (see Jetson D030-D033). Key structural difference: x86 "cache" is a VRAM cache over host RAM (PCIe-bound, 1.5-28 GB/s links); ours is page cache over NVMe (disk-bound, 0.57 GB/s) with no CPU/GPU split (UMA).

## D041 (indicative): upstream `--moe-cache-mib` on Qwen3-30B; ncu roofline
- Result: at 8 GB cache beats static `--n-cpu-moe` by +38% decode (51 vs 37 t/s), at 4 GB loses 34% (18 vs 28); upload-only cache needs ~70-75% hit rate. ncu: 222 GB/s, 40% of kernel time in tiny kernels.
- Jetson relevance: consistent with our Jetson D030 (upstream moe-cache loses on UMA at 64% hits). The "hit rate >= ~75% to win" threshold matches; we are below it at 62%. Nothing new to run.

## D042 (indicative): n-gram self-spec, perf, bpftrace, intake
- Result: `--spec-type ngram-mod` on Qwen3-30B K30: 2.4x (rewrite) / 3.0x (repeat), text identical, 0 drafts and +-0% on open chat. perf: no DRAM-bandwidth PMU on Zen 2. bpftrace: 0.79 ms/CPU layer. Rule: log `draft_n`/`draft_n_accepted`; benchmark bandwidth with working set >= 8x LLC.
- Jetson relevance: n-gram is a flag, no rebuild if our image's llama-server has `--spec-type` (pin 31288c9c6 is the same engine x86 used). Costs nothing on chat. Verify batch reads each expert once per batch, which is the lever for a disk-bound decoder (see analysis below). Bandwidth-microbenchmark rule applies to our fio ceiling (we already model 570 MiB/s, Jetson D031).

## D043 / D047: protocols (no results)
- Frozen overnight protocols; amendments: A1 download A/A (0.2% effect), A2 post-hoc decode-path KLD (ub 1). Rule: a batch-shape floor (KLD ~0.0058, top-1 ~96.5-97%) exists for the reference itself; gate equivalence against it, not text identity.
- Jetson relevance: adopt the same KLD floor language; our D025/D027 gates (KLD 2.7e-4) already well inside it. Add swap/page-fault monitoring to quiet checks, which our watchdog already does.

## D044 (speed rule met): cache + CPU-share beats static at 4/6/8/10 GB
- Result: C3 (cache + `--moe-cache-cpu-share 0.9`) beats static by +30..+76% at every budget with 3-6% less VRAM; hit rate 50%/73%/87%/92% at 4/6/8/10 GB; share 0 is best above ~90% hit; TTFT worse (prompt eval does not use cache). Absolute KLD gate was miscalibrated.
- Jetson relevance: CPU-share exists to compute misses on the CPU instead of uploading over PCIe. On UMA the "upload" is a no-op (D030 found the cache duplicates residency) and the miss cost is a disk read, so CPU-share does not help. Not worth running. The hit-rate-vs-budget curve is still a useful comparator for our replay sweep (LRU 62% @ 12.7% of model).

## D045: ngram spec ACCEPTED (static), stacks with cache; REAP-15B trade-off
- Result: static K30 ngram 2.32x/3.01x text identical, chat +1%; on cache arm 1.53x/1.68x (verify window touches ~19 distinct experts/layer for 4 drafts, extras are misses); cache + ngram 3.9x over static on repeat. Cache arm text depends on cache history. REAP-15B (pruned Qwen3-30B): all-GPU 242.7 t/s vs 36.7 (6.6x), code PPL +8%, wikitext PPL x2.84.
- Jetson relevance: ngram gain shrinks when extra experts are misses, which describes our disk-bound regime. Still positive on copy-heavy prompts. REAP: a pruned Qwen3.6-35B (if one exists) shrinks the model so more experts fit in page cache; 15B at Q4 ~ 9.75 GB is still > 7.4 GiB RAM so it remains over-memory but at a much higher hit rate (est. ~75% of model resident-ish vs 33% now). Domain-quality caveat (code only). Cost: 10+ GB download plus eval.

## D046 (accepted for copy; chat equivalent per D048 X2): MTP on Qwen3.6-35B-A3B
- Result: MTP n_max 3: +42%/+33% (rewrite/repeat) and +12% chat at K18, +40%/+27%/+12% at K30; chat acceptance 64-70%; costs +820-882 MiB VRAM; needs the `-MTP` GGUF (22.66 GB UD-Q4_K_M; ours is a different, non-MTP file) and `--spec-type draft-mtp`. Experts 1.81 MiB (our model, same arch `qwen35moe`).
- Jetson relevance: same architecture and model family as ours, so the MTP head gain transfers in principle, but our verify cost is disk bytes, not CPU/PCIe. See analysis.

## D048 (X1-X8, overnight 2)
- X1: MTP beats spending the same VRAM on GPU layers (+9.8% chat). X2: ub 4 verify batch KLD 0.00577 vs floor 0.00588, equivalent. X3: cache transfers to Qwen3.6 (+21..+42%). X4: CPU-share must be 0 or high, never small (fixed sync cost). X5: 4 threads beat 8 (+2-3%), SMT -50%. X6: ub 2048 cuts cache TTFT 2.9x for +0.97 GB. X7: mmap load 6.3 s warm / 18.8 s cold (1.48 GB/s); `-lm none` costs +10 s; keep mmap. X8: cache + MTP stack (+52% chat vs static; MTP gain on cache only +6.5% because extra experts are misses).
- Jetson relevance: X4/X3 CPU-share not applicable (UMA). X5: our CPU is mostly idle in decode (GPU+disk bound); thread counts affect only the page-fault path; a quick `-t 4` vs 6 check is cheap. X6: prefill on Jetson over-memory is pp64 2.49 t/s (Jetson D029); bigger ub reduces the number of full-expert sweeps per prompt, but ub buffers consume shared DRAM (x86 +0.97 GB at 2048 is 13% of our RAM). X7: confirms keep mmap (we already do). X8 stacking lesson: speculation gain falls when the verify window adds misses.

## Does spec decoding help a disk-bound decoder? (T-SPECM expert-union)
Per step a verify of n tokens reads the union of experts across n tokens per layer, not n times. x86 T-SPECM measured ~19 distinct experts per layer for 4 drafts on top-8 routing (8 for one token), i.e. ~2.4x the bytes of one token. MTP n_max 3 at 65% acceptance yields ~1 + 0.65 + 0.42 + 0.27 = 2.3 tokens/step (also ~2.4 at 66%). So bytes/token ratio is roughly 2.4/2.3 ~ 1.0 for chat: **break-even for MTP on chat when every expert is a miss**, a gain only as far as drafted tokens re-use experts already in page cache (hit rate 62% helps the second, third tokens of the window since the union overlaps the first token's experts and the cached hot set). For high-acceptance copy-heavy text (ngram: 3-5 tokens/step with routing that repeats across repeated content), union grows sublinearly, so the gain could approach the x86 factor (2-3x). Prediction method: replay our routing traces (4 captured, `cc/routing_trace`, `cc/expert_replay`) with a window-union model before spending a download.

## Top 3 Jetson experiments suggested by x86 results
1. **ngram-mod on over-memory Qwen3.6, copy-heavy vs chat prompts** (D042/D045). Expected: chat ~0 (no drafts, no cost); rewrite/repeat 1.5-2.5x if draft_n > 0 and text identical; decode rises above the 1.3 t/s disk ceiling because the verify batch pays disk once per window. Cost: low (flags only on the existing image/`llama-server`, ~1 hour, mmap run plus watchdog, ABBA x2; log `draft_n`). Must use the Jetson page-cache and quiet protocol (no concurrent builds).
2. **Window-union replay on our routing traces, then MTP if predicted > ~1.15x on chat** (D046/D048 X1, T-SPECM). Expected: replay (offline, minutes, zero hardware) tells us the miss-bytes/token ratio under LRU for n=2..4; MTP itself ~break-even to +15% on chat, +25% on copy if replay says unions overlap. Cost: replay low; MTP real run medium (22.66 GB `-MTP` GGUF download, ~1 h on NVMe 88 GB free, +0.9 GB shared DRAM which reduces page cache by ~12%, might cancel the gain).
3. **ub sweep (512 / 1024 / 2048) and thread check (`-t 4/6`) on over-memory prefill** (D048 X5/X6). Expected: prefill pp64 2.49 t/s improves only for long prompts (fewer full expert sweeps) while decode unchanged; risk: ub 2048 compute buffers push page cache out and slow decode. Cost: low (flag sweep, 1-2 h), but run with the memory watchdog and compare MemAvailable.
