# D015 — SSD-tier emulation via container memory limit (job-6e6b2d39b8; engine b0, mixE4K, --n-cpu-moe 24, own-file cold cache)
Class: MIXED. Transfers: the existence/shape of the page-cache cliff, I/O accounting method, cold-vs-warm discipline. Does NOT transfer: absolute t/s (discrete GPU, Zen2 CPU AVX2, PCIe, local NVMe, Linux page cache; target is unified memory with its own SSD).
Method: all expert weights file-backed in host memory (GPU holds attention+embeddings only: 572-576 MiB), `docker --memory L --memory-swap L`, posix_fadvise(DONTNEED) on the model file only (no host-wide flush), cgroup memory.peak and io.stat rbytes sampled at 4 Hz.
Result (pp512 / tg64, 3 reps; CONCURRENT COMPILE LOAD avg ~18 on 16 threads => speeds are lower bounds): limit -> tg t/s, SSD read: 1536m -> 129, 1.6 GiB; 1024m -> 79, 4.1 GiB; 768m -> 15, 28.8 GiB; 640m -> 3, 95.7 GiB; 560m -> 1, 135 GiB. All runs exit 0, no OOM kill.
Interpretation: working set ~ process anon (~400 MiB incl. CUDA/ggml buffers) + ~750 MiB expert bytes. Once the limit drops below it, decode becomes SSD-bound with heavy read amplification (reads >> useful bytes: 135 GiB for a run of a few hundred tokens). Advisor bound tokens/s <= effective SSD B/s / fetched B/token is consistent with the ~15 t/s point if nearly every expert is re-fetched each token (~160 MiB/token if all 192 activations miss).
Implication for the target: naive mmap + OS LRU has no notion of routing skew or layer order; an explicit hot-expert residency policy + prefetch/read-ahead control is the component to evaluate (trace-driven sizing in D014 gives the hit rate that policy needs).
Caveat to fix in a clean rerun: CPU contention; 1 repetition per limit; the 1536m row includes the initial model load reads.
