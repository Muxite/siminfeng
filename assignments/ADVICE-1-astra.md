# Advice request 1 (to gpt-6-astra, read-only; orchestrator = Claude, campaign c1)
Context. We are discovering METHODOLOGY and TOOLS for fitting a very large MoE (target: ~500 GB of weights into 128 GB of unified memory plus a 4 TB SSD) while keeping accuracy similar and tokens/s acceptable. The target is a UNIFIED-memory system; our development machine is DISCRETE (RTX 5070 Ti 16 GB VRAM + 48 GB host RAM + NVMe SSD). Our proxy model is ibm-granite/granite-3.1-1b-a400m-instruct (24 layers, 32 experts/layer, top-8, hidden 1024, BF16 2.67 GB), engine llama.cpp (build 11723) plus Strata (github Niko1221/Strata, expert slots/residency/CPU-GPU dispatch) studied as a reference.
Measured so far (Granite on llama.cpp): GPU memory (peak delta incl. CUDA ctx): BF16 2850 MiB, Q8_0 1658, Q4_K_M 1086. Decode t/s: BF16 599, Q8_0 794, Q4_K_M 710 (Q4 slower than Q8: K-quant dequant cost). Decode is ~90% GPU kernel time (graph exec 1580us/token) and ~10% host gap; the big MoE expert matvec reaches ~75% of DRAM peak, small projection kernels only 30-44% (latency-bound). Stock llama-eval-callback shows only 6 of 8 expert IDs per token (abbreviated print), so we wrote an out-of-tree routing tracer (full top-8 ids+weights per layer/token) and a trace-replay LRU/LFU slot-cache simulator.
Planned experiment families: uniform + mixed per-tensor quantization (experts low-bit, attention higher-bit), expert placement (--n-cpu-moe/-ot), KV-cache quantization, trace-driven residency sizing, SSD-tier emulation by running with a container memory limit below the mmap'd weight size.
