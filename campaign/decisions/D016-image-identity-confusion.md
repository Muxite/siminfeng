# D016 — Build CC recorded the wrong "image config id" (found by independent observation, T-K)
Evidence: experiments/handoff-real/verdict.json (first rejection), cc/engine_handoff/example-real/{facts.json,verdict.json}, archive builds/results/b0-baseline-3/engine-image.docker.tar (index.json top digest sha256:cf383f82..., manifest.json Config sha256:7c2b92ad...).
Finding: with Docker 29's containerd image store, `docker image inspect .Id` returns the OCI INDEX digest (cf383f82...), not the image config digest (7c2b92ad...). The Build CC (written by Codex T-D from the brief's own warning) still stored the inspect Id as the image identity; `lab image-load --expect-config-id` therefore "verified" a value that is not a config id. The handoff tool refused to admit it because it re-observed the archive instead of trusting the record. It also showed the record hashed 7 of 19 executables in /app (libraries omitted).
Why it matters: the brief says to distinguish archive hash, Docker config ID, platform manifest digest and index digest; a lab that loads the archive needs the identity that the receiving engine can actually check.
Fix: Build CC now records image.docker_reported_id, image.config_digest, image.index_digest, image.index_manifests (parsed from the saved archive) and app_files (all regular files in /app), with a note; unit test asserts they are separate. Admission (lab image-load) to use archive-derived ids (next).
Lesson (methodology + Manager): identity checks must be performed by an independent observer on the delivered bytes; a record written by the producer is a claim. Two CCs written independently agreed on field names but not on meaning.
