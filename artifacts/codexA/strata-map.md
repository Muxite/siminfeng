## 1. The three decisions

| Decision | Inputs → outputs | Owner and boundary |
| --- | --- | --- |
| **Routing: which experts and weights?** | Current normalized activation plus learned `ffn_gate_inp.weight` → expert IDs and mixture weights. | `moe_route` projects logits and selects top-k; it does not consult the expert cache. Its Qwen rule is softmax, stable descending selection with index tie-breaking, and renormalization. [`src/core/layer.cpp:405-423`; `include/strata/kernels/router_top10.hpp:3-5`] |
| **Residency: where are their bytes?** | `(layer, expert)` plus profile, capacity, and later usage → slot or `-1`, host copy, or file fallback. | `ExpertCache` owns device slots and its lookup table; admission does not evict, while driver-level adaptation handles replacement. Residency is not an expert computation. [`include/strata/core/expert_cache.hpp:19-21,93-100,154-167`; `src/program/generate.cpp:19839-19879`] |
| **Execution: who computes each routed contribution?** | Router IDs plus residency and transfer capabilities → GPU resident groups, GPU PCIe groups, peer/helper work, CPU jobs, then output rows. | `ExpertDispatch` and the session/verifier coordinate these paths; GPU execution is possible for an expert absent from the permanent VRAM cache. [`include/strata/core/expert_source.hpp:378-400,496-503,533-566`; `src/core/expert_source.cpp:4977-5048`] |

The normal dataflow is `activation → router IDs/weights → residency lookup → execution plan → expert vectors at router-indexed rows → weighted sum + shared expert → residual update`. The crucial invariant is that layer L's IDs, activation, output rows, and router weights stay together; the combine uses the current layer's weights, and the CPU job index can differ from the output-row index after hits are removed. [`src/core/layer.cpp:514-535`; `src/core/expert_source.cpp:4798-4823`; `include/strata/core/session.hpp:140-149`]

This separation has an explicit exception: **execution policy can alter the effective model**. `STRATA_ROUTE_TAIL_SKIP` omits a missed expert when every appearance in a verify window is at or below the configured rank; it leaves its contribution zero and does not renormalize the remaining weights. Serve startup can default the rank to 7 subject to architecture, cache-coverage, batch, peer, and NVFP4 conditions. Thus a placement-dependent omission is not merely a different execution location, even though the router IDs themselves remain available. [`src/core/expert_source.cpp:4941-4962,4981-4984`; `src/program/generate.cpp:12182-12214`]

## 3. Model identification and compatibility

The shared GGUF family detector recognizes exactly `qwen4exp` and `qwen35moe`; any other architecture maps to `Unknown`. Flash-Next's `model_family_runs` permits only `Qwen4Exp`, because Qwen35 is handled by its separate engine path. This detector is not a declaration that DeepSeek is unsupported by the entire product: DeepSeek's independent executable lies outside it. [`include/strata/artifact/model_family.hpp:15-25,51-62`; `src/program/generate.cpp:3270-3285`; `CMakeLists.txt:931-945`]

For native Flash-Next loading, the driver resolves all GGUF shards, locates the PLE table by tensor name, and requires it; `--native` turns on the native projection/router/GDN/QSA/PLE-related paths. Geometry is then read from model metadata and checked against the compiled geometry before loading proceeds. [`src/program/generate.cpp:4189-4228,4665-4691`]

The guards have two levels: `check_architecture` validates the architecture and its required metadata; `geometry_unsupported` pins Flash-Next dimensions, attention/indexer settings, hyper-connections, FF width, and RMS epsilon to the compiled implementation. `geometry_from_gguf` derives layer counts and shape relationships, while the second compiled-geometry check intentionally allows runtime expert count and top-k. Recognition of a GGUF container therefore does not imply a dimension-generic transformer engine. [`include/strata/artifact/gguf_reader.hpp:677-697,805-865`; `include/strata/core/family_layout.hpp:31-93,96-123`]

The Qwen35 loader independently requires the Qwen35 family, checks the complete GGUF tensor layout, and restricts head dimension to 256, SSM state to 128, convolution width to 4, expert count to at most 512, and top-k to at most 15. Its geometry explicitly has plain pre-norm residuals and dense attention without the Flash-Next sparse indexer. [`src/qwen35/q36_engine.cu:960-979`; `include/strata/core/family_layout.hpp:63-73`]

DeepSeek reads its own pack, builds `Geo` from pack fields, and rejects incomplete geometry or unsupported head/index dimensions and routing/hyper-connection limits. Its metadata names include `n_routed_experts`, `num_experts_per_tok`, compression ratios, KV/index-source layer IDs, Engram layers, and DSpark fields; these are a separate contract from `ModelGeometry`. [`src/dsv41/ds4_model.cu:550-585,2651-2666`]

**Granite coupling conclusion:** there is no Granite branch in the shared family mapping, and simply adding its architecture string would leave the compiled geometry, tensor naming/layout, attention/state, and router mathematics unresolved. A Granite port requires its actual model specification plus a family/execution adapter; neither the Qwen guards nor the DeepSeek pack contract establishes compatibility. This is an extraction inference, not an assertion about unspecified Granite dimensions or routing rules. [`include/strata/artifact/model_family.hpp:15-25`; `include/strata/artifact/gguf_reader.hpp:805-865`; `include/strata/core/layout.hpp:42-70`; `src/dsv41/ds4_model.cu:550-585,2651-2663`]

## 4. Weight bytes, layout, and expert identity

`WeightTable` is a name-to-`WeightRef` device-arena loader driven by `<pack>/index.txt`; tensor meaning is intentionally delegated to callers. It supports verbatim data, BF16 held in F32, F32, and F16 held in F32, and records quantization planes, source offsets, and activation format. BF16 re-narrowing and scale widening are storage transformations, not routing decisions. [`include/strata/core/weights.hpp:6-23,41-84`; `src/core/weights.cpp:176-205`]

`pool_bytes` prices the dense arena before allocation; `load` accepts a skip set so native projections/head forms can replace canonical bytes. Skipped rows retain metadata with null data and `resident=false`; here **resident means a dense tensor has canonical storage**, a different concept from expert-cache residency. Native projection references share scratch and require an ordered session stream. [`include/strata/core/weights.hpp:88-98,113-135`; `src/core/weights.cpp:273-300`; `src/program/generate.cpp:4867,4918,4935`]

The layout layer resolves names as `blk.<layer>.<suffix>` and exposes `check_layer` / `check_all` for shapes and GDN/QSA layer consistency. These are available validation routines; this map does not assume every production entry point invokes `check_all`, merely because it exists. [`include/strata/core/layout.hpp:42-70`; `src/core/layout.cpp:149-170`]

An expert's logical identity is **`(layer, expert ID)`**, not its cache slot and not its index within a token's top-k list. `slot_of` indexes the residency table by `layer*n_expert + expert`; dispatch separately preserves router destination rows through `dst` and CPU output offsets. Moving an expert to a new slot must preserve both logical identity and routed output position. [`src/core/expert_cache.cpp:746-769`; `include/strata/core/expert_source.hpp:378-383,533-566`; `src/core/expert_source.cpp:4816-4823`]

The canonical Q2_0 blob uses compiled activation width 2560 and FF width 640; native packs instead use per-layer formats, byte sizes, and offsets from `native_experts.txt`, including per-role GGUF shard names. `ExpertLayout` is process-wide, and all consumers ask it for blob layout; version 5 also carries the Hadamard contract. This supports multiple byte formats within the existing engine, not arbitrary expert dimensions. [`include/strata/kernels/cpu/expert.hpp:35-55`; `include/strata/kernels/cpu/expert_layout.hpp:1-6,18-37,92-101`; `src/program/generate.cpp:4425-4442`]

Expert weights can come from `FileExpertSource` mapping `experts.bin`, from native GGUF role slices assembled on demand when `experts.bin` is absent, or from `ArenaExpertSource` loading a host arena. The file source validates expected sizes and GGUF spans; the driver can fall back from an arena that cannot fit RAM to a file/resident-budget mode. A file-backed expert may be served from OS page cache, so “file tier” alone is not evidence of a physical SSD read. [`include/strata/core/expert_source.hpp:717-727,1268-1274,240-244`; `src/program/generate.cpp:7092-7115,7316-7337`]

## 5. Routing decisions: model mathematics

For Flash-Next, `moe_route` looks up the layer's `ffn_gate_inp.weight`, projects the current input in the BF16/native projection contract, and calls the native fused top-10 only for 512 experts and k=10; other supported widths use `router_top10`. Its output is IDs and renormalized weights, with no cache lookup in that function. [`src/core/layer.cpp:405-423`]

Window routing can batch BF16 projections and top-k across tokens; when that configuration does not qualify, it calls the per-token router. This changes the launch organization while retaining the per-token routing interface. The shared expert is evaluated separately, and the combine sums `weights[i] * parts[i]` plus the shared output. [`src/core/layer.cpp:440-465,468-475,514-535`]

DeepSeek instead projects its router with F32 weights. Its kernel computes `score=sqrt(softplus(logit))`, selects using `score+bias` with index tie-breaking, and derives the final weights from the **unbiased** selected scores normalized and multiplied by `route_scale`; image tokens may use a distinct bias. Replacing this with the Qwen softmax router would change the model. [`src/dsv41/ds4_model.cu:14262-14266`; `src/dsv41/ds4_kernels.cu:529-575`]

DeepSeek's `--experts` / Faster-mode rule can lower the model's top-k according to integrated GPU/card-memory and architecture conditions, with an explicit requested count taking precedence and a clamp to model k. This is a routing/quality policy, distinct from placing the selected experts in VRAM. The precise deployment rule must be taken from this revision rather than assuming every mode always evaluates all model experts. [`src/dsv41/ds4_model.hpp:49-54`; `src/dsv41/ds4_experts_rule.hpp:43-50`]

`RouterLookahead` is a **prediction for bytes**, not an alternative authoritative router: it applies future-layer router weights to the current activation to warm predicted experts, optionally into Foresight swap space, and skips work if a prior prediction is still running. Actual execution still classifies the real routed IDs. [`include/strata/core/expert_source.hpp:311-330`; `src/core/expert_source.cpp:4875-4881,4930-4938,4986-4999`]

## 6. Residency decisions: slots, profiles, replacement

`ExpertCache` allocates device storage and a `(layer, expert) → slot/-1` table. Uniform allocation uses `n_slots*blob_bytes`; sized allocation accommodates per-layer blob sizes. `slots`, `full_slots`, and claimed `resident` are distinct capacities/counts, especially after an elastic shrink. [`include/strata/core/expert_cache.hpp:93-117`; `src/core/expert_cache.cpp:571-601`]

`admit` returns an existing slot, otherwise claims a free global slot or one in a layer's quota; it refuses invalid IDs, full capacity, or a sealed cache. It does **not** choose an eviction victim. `replace` is a same-layer publication operation after the replacement copy completes; higher-level code owns the replacement policy. [`src/core/expert_cache.cpp:746-769`; `include/strata/core/expert_cache.hpp:162-188,222-228`]

The Qwen static profile uses `STRP` plus version/geometry/ranking metadata and ranked `(layer,expert)` pairs. The driver reads that ranking, resolves capacity, admits ranked pairs, copies their blobs, and reads back a startup slot to verify its bytes. A profile is a residency prior, not a replacement for learned router weights. [`include/strata/core/expert_cache.hpp:40-55`; `src/program/generate.cpp:5569-5579,8035-8073`]

Profile provenance matters: the reader checks STRP/version, layer/expert counts, ranked-list length, and pair bounds, but does not bind a profile to a weight-file digest. Also, `tools/make_profile.py` defaults to preserving the base ranking before adding trace pairs; with a base ranking every pair, new traces do not change the ordering unless `--reorder` or `--no-base` is selected. A profile's ordering should not automatically be treated as a fresh workload frequency measurement. [`src/core/expert_cache.cpp:170-229`; `tools/make_profile.py:8-19,73-97`]

Adaptive residency is implemented above the cache. In the non-serve path, missing experts with decayed usage at least 2 are paired with their layer's coldest residents, requiring usage gain at least 1.5; candidate swaps are globally ordered and capped. Pending copies become visible through the host/device residency tables only after their completion event; compact RAM complements exchange identities as well. Serve also exposes an `AdaptGate` to hold a layer's GPU plan until its replacement bytes have landed. [`src/program/generate.cpp:19808-19879`; `include/strata/core/verify.hpp:45-55`]

RAM residency can be a compact complement of the GPU cache, optionally pinned/mapped for direct transfers and PCIe access. A bounded variant keeps the hottest remaining experts by profile and leaves the rest in mapped files; prompt-loan experts may also need a retained host copy. RAM budget and GPU-cache budget therefore interact through which bytes must survive a loan or swap. [`include/strata/core/expert_source.hpp:735-760`; `include/strata/core/expert_source.hpp:156-166`]

DeepSeek has a separate moving expert cache and RAM/file lane, including a demand store with LRU/LFU/hybrid policy. Its swap-in routine uploads to a spare VRAM slot and can move an evicted expert back into RAM/store. Its profile is a bare array of u32 counts with size checks, not Qwen's STRP ranking format, and `save_profile` replaces it unless readonly. These two profile formats cannot be exchanged as-is. [`src/dsv41/ds4_model.hpp:36-48`; `src/dsv41/ds4_model.cu:8630-8659,14802-14811`; `src/dsv41/ds4_experts_rule.hpp:53-62`; `include/strata/core/expert_cache.hpp:40-55`]

## 7. Actual execution and CPU/GPU coordination

### Expert source versus execution adapter

`ExpertSource` supplies byte access (`blob`, stable blobs, and optionally three role parts), lifetime notification for asynchronous readers, pinning/device aliases, copy methods, and read-ahead. It does not specify an expert's learned selection rule. The ordinary blob may be recycled by a subsequent call, while stable/parts APIs are intended for long-lived asynchronous consumers; callers must honor `note_async_read` and transient-source contracts. [`include/strata/core/expert_source.hpp:184-211,216-239,249-267`]

`ExpertDispatch` binds this source to the CPU pool, optional primary cache, residency table, GPU plan sink, lookahead, and peer/helper tiers. Thus **the source interface is a storage seam; dispatch is the execution adapter**. The dispatch implementation still embeds Qwen-specific arithmetic and width restrictions, so extracting the seam is easier than reusing this complete adapter unchanged. [`include/strata/core/expert_source.hpp:493-566`; `src/core/expert_source.cpp:4724-4739,4888-4894`]

### Per-layer hit hook

The router publishes the current layer's activation, IDs, and weights to mapped handoff buffers and rings last on the ordered stream. `HitFn` is an independent header shared by session and adapter, with `Launch` before CPU work and `Combine` after the H2D miss copy; the hook takes the current IDs explicitly to prevent using a previous layer's hit list. [`src/core/layer.cpp:424-439`; `include/strata/core/hit_hook.hpp:3-6,13-21,28-39`]

The concrete loop is `pre[L] → ring observed → HitPhase::Launch → CPU pool → H2D parts → HitPhase::Combine → post[L]`. The launch path decides hits once, can admit/fill a newly available slot, stages slot/destination lists, zeroes the separate hit output, quantizes the current activation, and launches grouped GPU experts. The CPU consumes that same hit decision, leaves hit rows zero, and runs only the remaining jobs; combine adds hit output into the miss buffer before the layer consumes it. [`src/core/session.cpp:725-750`; `src/core/expert_source.cpp:5317-5378,5394-5425,4749-4758,4798-4828`]

The canonical CPU expert computes `down(swiglu(gate(x),up(x)))`; the pool shares the already quantized activation across experts. Router weights are deliberately not applied by this CPU callback: they are applied by the device combine. GPU hit quantization requires FP32 activation scales to match the canonical CPU scale contract rather than silently using an FP16 scale. This is a numerical contract to adapt, not just a transport detail. [`include/strata/kernels/cpu/expert.hpp:57-67,119-146`; `src/core/expert_source.cpp:4718-4720,4818-4823,5385-5406`; `src/core/layer.cpp:514-525`]

### Token graphs and verify windows

There is also a whole-token graph path: the host launches one captured graph, polls each layer's doorbell, runs the pool, fences its writes, then releases the GPU through a mapped flag. With a static `host_res`, the pool can classify hit rows without a `Launch` callback. Therefore the per-layer `HitFn` sequence explains one path, not every production decode mode. [`src/core/session.cpp:923-979`; `include/strata/core/expert_source.hpp:563-566`]

For verify windows, `expert_pool_dispatch_multi` groups repeated IDs across tokens into distinct expert jobs, increments usage, and publishes a GPU plan **before** CPU work. Entries retain destination row `token*k+j` and token index. Residency/peer/helper/Foresight eligibility is tested separately from the optional PCIe share; eligible pinned misses can be copied into temporary GPU staging or accessed via a mapped alias. GPU nonresidency therefore does not force CPU execution. [`src/core/expert_source.cpp:4865-4917,4930-4938,4964-5048`; `include/strata/core/expert_source.hpp:378-400,677-685`]

The verifier waits for a ring, optionally waits on adaptive-copy readiness, calls the multi-token pool, and uses publication flags to release grouped GPU work. `GpuPlanSink` distinguishes permanent VRAM groups from PCIe groups and supports DMA, direct mapped reads, or graph-side copies. This execution partition can be tuned by measured CPU/GPU costs through `PcieModel`; it does not replace the router's selected IDs. [`src/core/verify.cpp:3469-3508,3773-3777`; `include/strata/core/expert_source.hpp:384-408,409-475`]

The GPU work is concrete: verifier `post` chooses `native_expert_grouped` using the layer's native format or `moe_grouped_s2_window` for canonical experts. It runs the permanent VRAM groups, then waits for the PCIe-ready flag and runs those groups through the same grouped dispatcher; all-resident mode writes directly into parts and avoids CPU rows/doorbells. This is the point where an execution plan becomes actual expert kernel launches. [`src/core/verify.cpp:2338-2417`]

## 9. KV, session state, and reset boundaries

Qwen `SessionState` owns GDN recurrent/convolution state, per-QSA KV/indexer state, shared scratch, hyper-connection residual `R`, MoE buffers, and PLE token/history state. Layer-split sessions allocate only the stage's layer range while retaining global ordinals; this is not a universal transformer-session abstraction. [`include/strata/core/session.hpp:29-88`]

`session_zero` initializes or clears residual streams, clears owned GDN state, resets each QSA state, zeroes PLE convolution history, and resets preceding/current PLE token IDs to -1. The Metal branch resets its own running window instead. Expert cache/profile state is outside these fields and is not reset by this function, so a fresh sequence need not imply a cold expert cache. [`src/core/session.cpp:144-177`; `include/strata/core/expert_source.hpp:496-524`]

QSA KV has separate residency modes from **expert** residency: full device pools, host-backed streamed main-model pools with a smaller device window, or a drafter ring. It also has hybrid K8/V4, Q4, INT8, and unquantized storage branches. Reset clears live device buffers, indexer state, and the streamed mapping; it deliberately leaves the large authoritative host copy uncleared because positions are not read before the new sequence writes them. [`src/core/layer.cpp:734-765,981-1009`]

Speculation appends tentative KV/index keys and commits the accepted prefix's GDN/indexer/PLE state; later writes overwrite rejected-position KV. `Verifier::commit` validates the kept count, with a special one-token self-commit path and an explicit QFUSE exclusion. Thus resetting, rewinding, and committing are different state transitions. [`include/strata/core/verify.hpp:13-18`; `src/core/verify.cpp:3852-3865`]

Conversation persistence distinguishes running-state checkpoints from KV payloads: snapshot helpers validate geometry/range/byte limits and synchronize around save/restore; equal token IDs alone do not prove unchanged KV bytes. The Python engine adapter exposes `SAVE`/`RESTORE` between requests, with service-level coordination. This state transport is unrelated to the operator journal. [`include/strata/core/conversation_snapshot.hpp:12-57,59-79`; `serve/server.py:2724-2737`; `strata_control/journal.py:1-6`]

DeepSeek state includes window rings, compressor partial groups, compressed KV/index keys, and Engram history. Checkpoints keep the rewindable portions while slot save/load includes the full conversation payload. Its reset sets position to zero, clears tokens/checkpoint/mark state, clears rings and compressor accumulators, and synchronizes device streams; it does not reconstruct the loaded weight/expert tiers. [`src/dsv41/ds4_model.hpp:6-13`; `src/dsv41/ds4_model.cu:7116-7155`]

## 10. Memory budgeting

| Budget | What is priced / constrained |
| --- | --- |
| Dense + session | Dense `pool_bytes` is calculated before loading; `session_bytes` prices context, scratch, and per-layer state, optionally for a split range. The driver allocates session memory using that price. [`include/strata/core/weights.hpp:113-135`; `include/strata/core/session.hpp:91-102`; `src/program/generate.cpp:6376-6381,6412-6413`] |
| Auto expert cache | The rule starts from device memory free after other allocations, subtracts reserves/priced future costs, and can retain an extra 256 MiB for late allocations when minimum cache capacity still fits. The driver calls this rule and prices stage/session costs. This is a live-memory allocation policy, not a model parameter count estimate. [`include/strata/core/auto_cache.hpp:1-15,22-44`; `src/program/generate.cpp:5739,7558,7614`] |
| Actual allocation | `ExpertCache::open` compares requested bytes to device free memory; auto cache startup can retry at three-quarters size after allocation failure, and its touch/recheck logic addresses lazy residency under WDDM. [`src/core/expert_cache.cpp:571-601`; `src/program/generate.cpp:7904-7939`] |
| UMA / Windows | `device_free_bytes` documents UMA available-memory headroom rather than simply treating device MemFree as all usable RAM; a Windows opt-in also clamps against whole-card usage. Host budgeting includes available RAM, cgroup limits, and Windows commit capacity. These limits are not interchangeable with VRAM size. ## 11. Build paths and backend limits

The root CMake project defaults GPU options off and exposes separate CUDA, HIP, and SYCL selection. SYCL delegates to its own project and returns before the root target graph; CUDA/HIP are mutually exclusive outside the special gfx906 compatibility path. The root uses C++20 and builds GPU-free artifact utilities as well as conditional GPU targets. These are source build paths, not commands executed for this report. [`CMakeLists.txt:10-23,73-94,152-160,325-337`]

The libraries make a useful dependency boundary explicit: `strata_core` supplies runtime/loading pieces, kernel libraries depend on it, and composed layer/session/expert logic lives in `strata_engine` to avoid a core↔kernel dependency cycle. `strata` links that composition with prefill/speculation; Qwen35 and DeepSeek add their own target implementations. [`CMakeLists.txt:432-444,525,699-709,893-896,918-945`]

Metal is a separate macOS-only CMake project, using shared host sources through CUDA-name compatibility headers over Metal runtime/engine implementations. SYCL uses shared sources where possible and migrated copies where needed, with SPIR-V JIT or optional device AOT. Backend-named header compatibility therefore does not establish identical kernels, available families, or memory features. [`metal/CMakeLists.txt:1-17`; `sycl/CMakeLists.txt:1-11`; `include/strata/artifact/model_family.hpp:51-62`; `src/core/expert_cache.cpp:4-8`]

The root builds DeepSeek only with `STRATA_BUILD_DSV41` enabled and excludes that target under the special gfx906 path; it links its own model/kernels and optional shared CPU trellis code. The presence of DeepSeek-related Metal branches in sources should not be conflated with a tested/released hardware combination; this report establishes code structure only. [`CMakeLists.txt:931-971`; `src/dsv41/ds4_model.cu:2828-2834`; `AGENTS.md:96-97`]

## 13. `strata_control/journal.py` and `calibration_jobs.py`

`journal.py` is an **operator-operation journal**, not an expert trace, KV session log, or inference replay stream. It stores bounded identities, typed intents, revision references, compact outcomes, and running/terminal events; it deliberately excludes full request bodies, credentials, and full calibration reports. Running after a caller crash means completion is unverified, not proof of a live worker. [`strata_control/journal.py:1-6,25-44,252-255,321-328`]

Records live in a private per-profile `.runs` directory, with validated IDs, owner-only file checks, a 64 KiB size limit, and a 500-record cap that prunes terminal runs. Schema 1 is recipe-based; schema 2 is direct operator intent. Direct starts validate the current profile revision, and `finish` permits a single transition out of running through atomic replacement. [`strata_control/journal.py:25-69,190-221,259-318,331-378`]

`run_direct` wraps an authorized action and distinguishes failed from `completion_unknown` for interruption/uncertain exit code 8; result compaction records bounded runtime/bench/calibration fields. This is a reusable control-plane pattern, but its concrete intent/result schemas depend on Strata's profiles, recipes, and runtime APIs. [`strata_control/journal.py:381-429,78-99`]

`calibration_jobs.py` wraps reviewed desktop `measure`, `apply`, and `rollback` operations with journal receipts. `create` records profile/source/report preconditions and the job ID; `run` requires those exact reviewed parameters and acquires a per-profile worker lease. The lease uses nonblocking `flock` or a Windows byte lock plus an identity marker, so activity checks do not rely only on a PID or journal state. [`strata_control/calibration_jobs.py:20-23,38-118,207-244`]

Execution reruns source/precondition checks inside the receipt, requires exclusive-access acknowledgement, and invokes `calibration.measure` with progress/cancellation callbacks. Apply/rollback require the reviewed report body hash; they call separate calibration mutation routines. A successful measurement does not itself mean its settings were applied. [`strata_control/calibration_jobs.py:273-319`; `strata_control/calibration.py:289-333`]

Progress is supplementary typed state (`preflight`, loading, PCIe share, draft floor, CPU workers, expert tier, saving report, and other allowed stages). Cancellation is a private marker accepted only for the exact active measurement; a watcher turns it into an event. Completion is reconciled with a saved report only when operation ID, profile/revision, and source digest match. Status distinguishes active, launching, completion unknown, failed/cancelled, and recovered-report success. [`strata_control/calibration_jobs.py:20-23,121-180,247-269,322-404`]

The underlying measurement code snapshots engine/config/hardware identity, invokes the calibration runner, validates returned settings, rechecks identity, writes a report with an applicability flag and body hash, and associates it with the operation ID. Calibration is therefore configuration evidence and controlled application machinery, not a hidden replacement router or a per-token cache controller. [`strata_control/calibration.py:146-167,270-287,289-333`; `strata_control/calibration_jobs.py:295-309`]

## 15. Open questions and static-analysis limits

- **Which exact Granite variant and artifact format is the target?** The current family mapping and both engines' geometry contracts are insufficient to infer its router, dimensions, shared experts, attention, or state reset requirements. [`include/strata/artifact/model_family.hpp:15-25`; `include/strata/core/geometry.hpp:23-67`; `src/dsv41/ds4_model.cu:550-585`]
- **What numerical contract is required across tiers?** The canonical CPU/GPU scale rules, optional oracle CPU arithmetic, prefill CPU sharing, and missed-tail omission must be controlled before claiming placement-invariant output. No such parity has been executed here. [`include/strata/kernels/cpu/expert.hpp:57-67,111-117`; `src/core/expert_source.cpp:5385-5406,4941-4962`; `src/prefill/prefill.cpp:271-275`; `AGENTS.md:96-97`]
- **Which production configuration is the intended baseline?** Family, backend, native pack, cache/profile, resident budget, KV mode, batch slots, draft source, and environment flags select materially different paths; source defaults alone do not identify an actual run. [`src/program/generate.cpp:4189-4228,5569-5579,12182-12217`; `src/core/layer.cpp:734-765`; `serve/server.py:3492-3515`]
- **What trace schema should a new analysis pipeline consume?** Qwen single-token true weights, Qwen multi-token placeholders, and DeepSeek binary records need explicit discrimination; counting routed IDs is different from measuring contributions that were actually computed after skipping. [`src/program/generate.cpp:1388-1427`; `src/dsv41/ds4_model.cu:9433-9437,11748`; `src/core/expert_source.cpp:4941-4962`]
- **Should learned placement persist across model/session changes?** Qwen STRP geometry/ranking and DeepSeek count-array profiles differ, and model reset does not clear the expert tiers. A reusable layer needs an explicit model identity and persistence policy beyond matching table dimensions. [`include/strata/core/expert_cache.hpp:40-73`; `src/dsv41/ds4_experts_rule.hpp:53-62`; `src/core/session.cpp:144-177`; `src/dsv41/ds4_model.cu:7116-7136,14802-14811`]
- **Which backend capabilities and hardware limits are required?** Stable-address elastic storage, mapped pinned transfers, available quant kernels, and family entry points differ by backend; build targets and source guards are evidence of implementation boundaries, not measurements of availability or performance on a particular machine. [`CMakeLists.txt:14-21,80-94,931-971`; `metal/CMakeLists.txt:1-17`; `src/core/expert_cache.cpp:4-8`; `include/strata/artifact/model_family.hpp:51-62`; `AGENTS.md:96-97`]

### Comment hazards when extending this map

Several comments preserve earlier development phases: `ExpertDispatch` still says every expert is computed on CPU, and the `expert_hit_run` declaration describes an after-misses placement; the active implementation runs GPU hits and uses separate Launch/Combine phases. Treat those historical paragraphs as design history and follow the executable call order. Likewise, multi-token routing trace comments say unit weights while the code writes zeros. [`include/strata/core/expert_source.hpp:510-519,687-693`; `src/core/session.cpp:725-746`; `src/core/expert_source.cpp:5399-5425`; `src/program/generate.cpp:1417-1427`]
