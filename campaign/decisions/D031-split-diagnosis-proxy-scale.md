# D031 — Why the hybrid split loses on Granite (nsys, T-PROF) and the proxy-scale bias it reveals
Evidence: artifacts/codexPROF/ANALYSIS.md, cc/nsys_decode/analyze_nsys.py (new profiling CC), artifacts/x4-hs/prof/{split,static}-n12.sqlite (graph-level, same binary, 154 decode tokens after 5 warmup).
Per token: static n12 5.35 ms (13 graph launches, 110 syncs, GPU busy 1.06 ms = GPU idle ~80%); split n12 7.38 ms (25 graph launches, 194 syncs, GPU busy 2.55 ms). Extra 2.03 ms = 1.45 ms extra GPU graph work (per-slot hot dispatch: 1535 vs 583 kernels in first decode) + 0.37 ms exposed sync/transfers + 0.21 ms host. CUDA graphs ARE reused (no capture loss).
Interpretation (orchestrator): at batch 1 on this host, decode is dominated by per-layer CPU<->GPU handoff latency, not by expert bytes or GPU compute. The split computes FEWER CPU experts per token (~52 vs 96 at ~73% hot coverage) yet is slower because it pays the handoff in 24 layers instead of 12. T-PROF's best redesign (batched CUDA dispatch with skip IDs, -0.7..-1.1 ms) would only reach ~parity with static.
Transferability (key factory lesson): Granite experts are 0.84 MiB; the target (~500 GB MoE) has experts ~10-50x larger, so per-layer fixed costs amortize and expert-granular placement (hot GPU / cold CPU, Strata-style) should regain its advantage. Granite-only results systematically favour layer-granular placement. => The factory needs a second proxy that genuinely exceeds VRAM with larger experts before deciding placement granularity; Granite results on placement are labelled "small-expert regime".
Methodology rule: report per-layer fixed cost (handoff latency) alongside per-expert cost; predict crossover expert size = fixed_cost / per_byte_cost before choosing granularity.
