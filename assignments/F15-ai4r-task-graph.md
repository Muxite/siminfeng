## Context
AI4Research-Main (`141c1c4`) planned research as a task graph: read (via `git show 141c1c4:<path>`) `jiuwenswarm/research/{planning.py,unified_planning.py,capability_planning.py,scheduler.py,pi_task.py,planner_catalog.py}`, `jiuwenswarm/research/capsules/planner.py`, `jiuwenswarm/symphony/{graph_state.py,graph_storage.py}` and the architecture docs of that revision. Our branch (`ai4r/iterative-cc-factory`, CC-v2 donor) deleted those and runs an iterative agent controller (`jiuwenswarm/factory/`): the agent publishes `decision` revisions (CAS on `expected_rev`) into the SQLite evidence store and invokes CCs; builds/lab runs are durable jobq jobs. `docs/architecture/factory/MIGRATION.md` maps old→new. What's missing is the AI4R notion of a **task graph**: the visible plan of work items with dependencies, owners (CC capabilities), states and evidence — but unlike M1 it must be **revisable by the agent from evidence** (add, cancel, retry, reorder nodes) instead of a fixed pipeline compiled up front.

## Build
1. `jiuwenswarm/factory/taskgraph.py`: a task graph stored in the evidence store (new append-only tables or evidence records — follow store.py conventions: task-scoped, append-only, CAS):
   - Node: `{node_id, kind (inspect|integrate|build|measure|tune|investigate|decide|accept|report), title, capability (CC id.capability or null), inputs (refs), depends_on [node_ids], state (proposed|ready|running|blocked|done|failed|cancelled|superseded), attempt_ids, evidence_ids, created_by_decision_rev, reason}`.
   - Graph operations are **patches** `{add:[node], update:[{node_id, state?, evidence_ids?, attempt_ids?}], cancel:[{node_id, reason}], supersede:[{node_id, by, reason}]}` applied with `expected_graph_rev` (CAS), each citing the decision revision that justified it. History is never rewritten: the graph at any revision is replayable from patches.
   - Validation: acyclic; depends_on must exist; a node can't be `done` without evidence_ids; `measure`/`build` nodes must cite attempt ids; cancelled/superseded are terminal; readiness = all deps done.
   - Derive node state from durable job state where linked (attempt succeeded → done candidate; failed → failed) — a reconcile function, no polling loops.
2. Expose to the agent through the existing `factory.evidence` capsule (or a new `factory.plan` capsule — your choice, justify): capabilities `plan_get{rev?}` (graph + ready frontier + blocked reasons) and `plan_patch{patch, expected_graph_rev, decision_rev}`. Keep calls fast (<1 s). Add a decision-schema hook: a decision MAY carry `plan_patch` which is applied atomically with the decision publish (if that is cleanly doable without big controller changes; else a separate call and document the order).
3. Seed: on task init, controller creates an initial **proposed** graph from the task (inspect → applicability → baseline build → measure baseline …) as a SUGGESTION node set the agent may cancel/rewrite — implement as a pure function `initial_plan(task)` in taskgraph.py plus a one-line call site in controller (guarded so a missing function doesn't break the other worker's changes).
4. CLI `jiuwenswarm factory plan <task> [--rev N] [--dot|--json]` printing the graph (text tree with states, `--dot` Graphviz) and the revision history (which decision changed what). Monitor/story hooks: provide `render_text(graph)` and `to_json(graph)` helpers; add at most small calls in story.py/monitor.py (monitor: a JSON endpoint `/api/plan?task=` returning to_json + a minimal collapsible panel if monitor.html structure allows; keep it small).
5. Telemetry: emit `factory.telemetry/1` events for plan patches (see telemetry.py) so the RSI side sees plan revisions.
6. Docs: `docs/architecture/factory/TASK-GRAPH.md` — how this evolves M1's planner/scheduler (concept-by-concept table: M1 planning.py/unified_planning/scheduler/graph_state → factory taskgraph/controller/jobs), what's intentionally different (graph is a revisable record, the agent proposes patches, the host validates and owns execution authority, durable jobs are the scheduler), and an example graph with a revision (e.g. measure node fails → investigate node added → integrate node superseded).
