# Model + GGUF candidates for Jetson Orin Nano 8GB Super (2026-11-11)

Method: all repos/filenames/sizes verified via `https://huggingface.co/api/models/<repo>/tree/main` (sizes in GiB, as listed by HF; no files downloaded). Benchmarks are from official model cards (raw README.md of each `Qwen/*`, `google/*`, `openai/*` repo) unless noted. llama.cpp latest release tag seen on GitHub: v0.9.0 (2026-11-04).

## 0. Estimation assumptions (our formulas)
- DRAM-fit: tok/s = (102e9*0.6)/bytes_read_per_token, bytes read = file size minus embedding table (and for Gemma E-models, minus Per-Layer-Embedding lookups, taken as effective 4.5B of 8B params). This is a ceiling-style estimate; real CUDA/CPU llama.cpp on Orin Nano is typically below it.
- Over-memory MoE: tok/s = SSD(570 MiB/s) / (routed_bytes_per_token * (1 - hit)). routed_bytes = routed_active_params * file_bpw/8 (file_bpw = file bits / total params; slightly overestimates expert bpw). Hit rate calibrated on our measured point: Qwen3.6-35B-A3B Q4_K_XL (20.8 GiB) = 1.4 t/s => implies hit ~0.245 at 20.8 GiB; scaled hit = 0.245*(20.8/file_GiB), capped 0.85 (i.e. uniform-routing cache model; our replay data say real LRU hit rates are better than uniform, so this is conservative; the model itself predicts 1.2 t/s for the calibration point, ~15% under measured).
- Routed params/token: Qwen3.6/3.5-35B-A3B = 40 layers x 8 experts x 3x2048x512 = 1.007B (config.json: 256 experts, top-8, moe_intermediate 512, plus 1 shared expert of 512, hidden 2048); Gemma-4-26B-A4B = 30 x 8 x 3x2816x704 = 1.43B (128 experts, top-8 + 1 shared; config); gpt-oss-20b = 24 x 4 x 3x2880x2880 = 2.39B (32 experts, top-4; config).
- Interesting consequence: Qwen3.6's fine-grained experts make it the cheapest per-token SSD traffic of the three big MoEs (~0.57 GB/token at 4.5bpw vs 0.80 Gemma, 1.27 gpt-oss).

Caveat: i-quants are 5-10% slower in compute (Unsloth, https://unsloth.ai/docs/models/qwen3.5/gguf-benchmarks) - irrelevant when SSD-bound, relevant for A-tier if IQ quants are used (use Q4_K/Q8_0 there). Thinking models emit thousands of tokens; at 2-3 t/s a thinking answer can take many minutes, so for the over-memory MoE consider `enable_thinking=false` (Qwen3.5 card, "Instruct (or non-thinking) mode") and note published scores above are thinking-mode and will not transfer. MTP/self-speculation: Unsloth claims 1.4-2.2x on GGUF for DRAM-resident models (https://unsloth.ai/docs/models/mtp), needs ~2 GB extra memory, smaller gains on low-bandwidth devices; our earlier SPEC1/SPEC2 over-memory experiments were negative, so only test MTP on A-tier.

## 3. Ranked shortlist (download in waves; resident disk <= ~25 GB)

Wave 1 (22.2 GiB = 23.8 GB):
1. `unsloth/Qwen3.5-9B-GGUF` `Qwen3.5-9B-UD-Q4_K_XL.gguf` 5.56 GiB - best accuracy that plausibly fits DRAM (MMLU-Pro 82.5, GPQA-D 81.7, IFEval 91.5 thinking); expected ~6-11 t/s, i.e. goal-to-stretch tier. Fall back to `UD-Q3_K_XL` 4.71 if memory-tight.
2. `unsloth/Qwen3.6-35B-A3B-GGUF` `Qwen3.6-35B-A3B-UD-IQ3_S.gguf` 12.74 GiB - same model as today, expected ~2.5 t/s (vs 1.4). Published KLD for a comparable 3.26-bpw IQ3_S: 0.084 (PPL +6.7%) vs Q4_K_M 0.0137, so ~6x higher KLD than Q4; measure it on-device. Highest absolute accuracy of anything reachable (MMLU-Pro 85.2, GPQA 86.0 at BF16).
3. `unsloth/gemma-4-E4B-it-qat-GGUF` `gemma-4-E4B-it-qat-UD-Q4_K_XL.gguf` 3.93 GiB - only candidate with an official QAT checkpoint and published KLD (mean 0.0012, top-1 98.5%) at small size; MMLU-Pro 69.4 is lower than Qwen3.5-4B (79.1) so it is the "QAT-fidelity" entry, not the accuracy leader.
Wave 2 (delete wave-1 Qwen3.6 file first):
4. `unsloth/Qwen3.5-4B-GGUF` `Qwen3.5-4B-Q8_0.gguf` 4.17 GiB + `Qwen3.5-4B-UD-Q4_K_XL.gguf` 2.71 GiB - speed-tier (stretch 10 t/s) pick and the practical KLD pair: Q8_0 as near-lossless reference (Unsloth: 8-bit mean KLD ~0.003 on Qwen3.6-27B) vs Q4_K_XL. True BF16 reference is `Qwen3.5-4B-BF16.gguf` 7.85 GiB (fits DRAM-ish; only 4B is feasible - 9B BF16 is 16.7 GiB). Warn: `llama-perplexity --kl-divergence-base` stores ~vocab(248k)x2 B per token (~0.5 MB/token); 512-ctx x 30 chunks ~ 7-8 GB, so cap chunks.
5. `unsloth/Qwen3.6-35B-A3B-GGUF` `Qwen3.6-35B-A3B-UD-IQ2_M.gguf` 10.73 GiB - speed fallback (~3.4 t/s) if IQ3_S accuracy tests fine and we want margin; accuracy risk at 2.7 bpw.
6. `unsloth/gemma-4-12B-it-qat-GGUF` `gemma-4-12B-it-qat-UD-Q4_K_XL.gguf` 6.26 GiB - optional: MMLU-Pro 77.2 / GPQA 78.8 but memory-borderline and weakest QAT KLD (0.133); only if wave-1 shows spare DRAM.
Skip: gpt-oss-20b (0.8 t/s est), Gemma-4-26B QAT (1.2 t/s), Qwen3.5-35B-A3B (dominated by 3.6), 27B/31B dense.

## 4. On-device accuracy sets (both have published per-model scores in the cards above)
1. MMLU-Pro (reported by Qwen3.5/3.6 and Gemma 4 cards; gpt-oss via Qwen table). HF dataset `TIGER-Lab/MMLU-Pro` (MIT, not gated), 12,032 test questions, 10-choice. Test: https://huggingface.co/datasets/TIGER-Lab/MMLU-Pro/resolve/main/data/test-00000-of-00001.parquet (4.1 MB, HTTP 200 verified); few-shot validation: https://huggingface.co/datasets/TIGER-Lab/MMLU-Pro/resolve/main/data/validation-00000-of-00001.parquet. Use a fixed-seed stratified ~300-500 question subset; compare relative ordering/deltas between quants, not absolute numbers (cards use thinking + long budgets).
2. IFEval (reported for Qwen3.5-9B 91.5 / 4B 89.8 / 35B-A3B 91.9 / gpt-oss-20b 88.2): `google/IFEval` (apache-2.0, not gated), 541 prompts, https://huggingface.co/datasets/google/IFEval/resolve/main/ifeval_input_data.jsonl (207 KB; jsonl not parquet; needs the `instruction_following_eval` checker). Cheap, non-thinking friendly, sensitive to quantization damage in instruction following.
Backups: `allenai/ai2_arc` ARC-Challenge test https://huggingface.co/datasets/allenai/ai2_arc/resolve/main/ARC-Challenge/test-00000-of-00001.parquet and `openai/gsm8k` https://huggingface.co/datasets/openai/gsm8k/resolve/main/main/test-00000-of-00001.parquet (both ungated; no per-model scores in the cards above). GPQA-Diamond (`Idavidrein/gpqa`) is gated=auto (needs HF login/accept) and MMLU-Redux 2.0 (`edinburgh-dawg/mmlu-redux-2.0`, cc-by-4.0) ships as per-subject .arrow files, not parquet (e.g. `anatomy/data-00000-of-00001.arrow`) - fine but more fiddly.
