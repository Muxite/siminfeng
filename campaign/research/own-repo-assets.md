## 1. Direct answers
**Can cc/routing_trace capture qwen35moe at 31288c9c6? Mostly yes after a 3-line patch edit.**
- Hook: `cb_eval` on exact names `ffn_moe_topk-N` (I32 {k,T}, strided view of argsort) plus `ffn_moe_weights-N` and the optional `_softmax/_norm/_scaled-N` stages. These are emitted by the shared `build_moe_ffn` (src/llama-graph.cpp:2273-2312). `src/models/qwen35moe.cpp:497` calls `build_moe_ffn`, so Qwen uses the same path. Shared expert (`ffn_shexp`) is not routed and is not traced. That is correct, but means no shared-expert data.
- Hardcoded Granite assumptions in `routing-trace.patch`: `value >= 32` ("expert ID outside [0,32)") will abort on the first Qwen layer (256 experts); `k == 8` is correct for Qwen3.6 (8 active) but hardcoded in 6 places. Fix: read `llama_model_n_expert`/`hparams.n_expert_used` and pass them in (~10 lines). `trace_replay.py` also hardcodes `32` (L62, L94, L113 histogram) and capacities (4..24 slots): do NOT use it for Qwen. Use `cc/expert_replay` (no hardcoded dims, `--layers 40 --experts 256`).
- Other Qwen risks: (i) hybrid DeltaNet layers still have an MoE FFN every layer (`GGML_ASSERT(ffn_gate_inp != nullptr)`), so the "every layer must emit" check holds, but confirm `llama_model_n_layer` excludes any MTP/nextn layer (hparams.n_layer() vs n_layer_all); (ii) it chunks prefill by `min(n_batch,n_ubatch)` and needs `-c` and `--no-warmup`; (iii) `cb_eval` forces per-range syncs: expect large slowdown with a 20 GiB mmap'd model (use it for routing capture only, never for timing); (iv) parser is `LLAMA_EXAMPLE_COMMON` so `-cmoe/-ncmoe/-ot/-mmp` should be accepted (verify with `--help`).
- Status: README says "not compile-linked", but that is stale. D014 records a real build (rt1, 18 s via ccache) and real Granite traces (`lab/tests/trace1.json`, `artifacts/traces/out/*.jsonl`). Real-run evidence exists for Granite only. Build CC packaging prerequisite (Dockerfile must build/copy `llama-routing-trace`; TOOLS list) was needed on x86; check the Jetson build recipe (cc/build_engine) copies it.

**What D015 / D019 / job-d50c052f94 measured**
- job-d50c052f94 (Granite mixE4K, `--n-cpu-moe 24` = ALL experts on CPU, `LLAMA_ARG_MOE_CACHE_MIB`, 160/96 decode tokens, 1 run per point, unscored class: discrete-only absolutes). GPU MiB grows 1:1 with the cache (773 -> 1413). Output text identical across cache sizes (same stdout sha). - D015 (`lab/tests/ssd1.json`, docker `--memory` limit, fadvise DONTNEED on own file): limit 1536m: 129 t/s, 1.6 GiB read; 1024m: 79, 4.1 GiB; 768m: 15, 28.8 GiB; 640m: 3, 95.7 GiB; 560m: 1, 135 GiB read. Caveats: compile load avg ~18 during the runs (lower bounds), 1 rep, no OOM kills.
- Predicts Jetson (transferable shape): the existence and sharpness of the cliff, read amplification of naive mmap + kernel LRU, bound tg <= (effective NVMe B/s) / (fetched B/token), and cold/warm discipline (fadvise on the model file only, report io rbytes). - `--moe-cache-mib` on Jetson: help text says "GPU cache ... for experts kept in CPU" (common/arg.cpp:2782; src/llama-moe-cache.cpp, LRU slots, CUDA backends). On Tegra the cache is a second copy in the same DRAM that the page cache needs, so expect it to take page cache from the 7.4 GiB and be a net loss at small sizes; worth one sweep (it is only the "competent-user baseline", NEEDS-MAP row 45). It does not change what NVMe has to supply.

## 3. cc/gpu_budget on Jetson (cooperative cap?)
- Covered: cudaMalloc, MallocManaged, MallocAsync, Free/FreeAsync (adds a stream sync), MallocPitch, Malloc3D (synthesized), cudaMemGetInfo, cuMemAlloc_v2, cuMemAllocAsync, cuMemFree_v2/FreeAsync, cuMemGetInfo_v2. Single process-wide counter, JSONL log, hard denial returns cudaErrorMemoryAllocation, env `GPU_BUDGET_MIB/RESERVE/COUNT_MANAGED/LOG`.
- Missing: cudaMallocHost / cudaHostAlloc / cuMemAllocHost / cuMemHostAlloc (ggml pinned host buffers, ggml-cuda.cu:1324; on Tegra this is also DRAM), cudaHostRegister (`GGML_CUDA_REGISTER_HOST`), cuMemAllocManaged, cuMemAllocPitch, VMM (`cuMemCreate`/`cuMemAddressReserve`, ggml-cuda.cu:627), `cudaMallocFromPoolAsync`/mem pools, cudaMallocArray. No obvious compile bug (`-std=c99 -Werror` build.sh passed on x86); weak points: dlsym on every call, one global mutex held across the real allocation, thread-local `nesting` only guards re-entry.
- Decisive Jetson problem: cudaMemGetInfo virtualization is bypassed by llama.cpp. `ggml_backend_cuda_device_get_memory` (ggml-cuda.cu:5429-5460) calls cudaMemGetInfo, then if `prop.integrated` (Orin) OVERWRITES `*free` with `/proc/meminfo` MemAvailable (`ggml_backend_cuda_get_available_uma_memory`, 5352). So the shim's virtual free never reaches auto-fit or `--fit` (D023's n_ctx 45568 would recur); only `total` is faked. A second path (`ggml_backend_cuda_get_device_memory`, 5283) does use the faked value. The only effective part is hard denial of device cudaMalloc, which does not constrain mmap'd CPU-resident experts or page cache. Net: usable as a hard cap on GPU-resident bytes (weights/KV/compute buffers) if cudart is dynamically linked (static cudart bypasses LD_PRELOAD; verify with `ldd /app/llama-*`), NOT as a steer for autofit or a limit on host-pinned/page-cache DRAM. For the over-memory experiment the physical limit is the budget; pin `-c`, `-ngl`/`-ncmoe` explicitly instead.
