Methodologies that held up

Measurement

  • Same image, environment switch per arm: isolates the code path from build noise.
  • Counterbalanced ABBA, two or more runs per arm, drop the first sample (GPU clock ramp), report steady mean.
  • A/A before trusting a delta: spread was ≤0.3 t/s at 50–100 t/s, so +10 t/s effects are unambiguous.
  • Keep compiles, simulators and downloads out of timing windows; mark contaminated runs instead of dropping them.

Quality

  • Decode-only kernel changes need -ub 1 perplexity and KL against saved base logits.
  • Scale every KL against a known reference (Q8_0 vs bf16: 3.4e-3).
  • Distinguish byte-identical (quantized unfuse) from small rounding change (bf16 MMF).

Platform hygiene

  • On shared memory, pin every free-memory-derived default (-c, load mode).
  • A fair over-memory baseline is what a competent user runs (-lm mmap, -ncmoe), with the default's failure reported separately.
  • Per-component applicability tables: weight type × compute capability × batch.

Process

  • Profile → cheap screen with an existing switch → targeted patch → counterbalanced A/B → KL → independent review → kernel inventory.
  • Search upstream before building: the moe-cache series landed days before we needed it.
  • Never stage a directory a running job writes to (a 1.4 GB archive nearly reached GitHub, D024).

What predicts, what correlates

Good predictors

  • Effective GB/s per kernel (weight bytes ÷ nsys time) pointed at every gain we found.
  • Bytes moved per token ÷ achieved read bandwidth predicts over-memory decode within ~10%.
  • Replay-simulated LRU hit rate landed close to the engine's own counter.
  • A/A spread sets the smallest effect worth chasing.
  • Byte-identical outputs predict a safe, computation-preserving change.

Poor or misleading predictors

  • Cache hit rate does not predict speed on unified memory.
  • Bytes per weight fails once kernels are dequant or compute bound.
  • Batch-512 perplexity is blind to decode-only kernel changes.
  • Single-layer or microbenchmark speedups are hypotheses until end-to-end.
  • Free-memory readings, container limits and binary hashes: each looked like a measure of budget or identity and wasn't.
  • Raw t/s across hosts: never comparable; only local A/B ratios are.
  • Routing frequency from other workloads does not predict which experts the next workload needs; recent use does.
  • Pure frequency (LFU) is a poor cache policy here (35% vs 62% LRU at 12.7%).

Structure and flexibility

Where structure paid off

  • Recorded commands and attempt IDs caught false successes: an exit code masked by a pipe, a watchdog that couldn't kill, a run that crashed after logging success.
  • Fixed identities (model hash, commit, patch hash, image digest) made cross-run comparisons trustworthy.
  • Per-host evidence folders, admission records and claim classes kept findings from being promoted without evidence.

Where flexibility paid off

  • Most progress came from fast throwaway screens: an existing env switch found the +14% before any patch.
  • Designs turned out model × hardware specific, so fixed recipes would have been wrong; env-gated components with applicability tables worked.
  • Swapping in upstream code beat building our own cache.

The working balance: rigid at the boundaries (identity, recording, admission, safety, quality gates), loose in the middle (which experiment to run next, which tool to try). About half the defects found tonight were in our own tooling, all caught because the boundaries were strict.
