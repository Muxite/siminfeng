## Q1: what the pinned engine does

All paths are relative to `../llama-place/`. `-cmoe` creates a CPU tensor-buffer override (`common/arg.cpp:2731`, `common/common.h:1259`, `common/common.h:1267`). The loader matches whole tensor names, first matching override wins (`src/llama-model-loader.cpp:1251`). It may consider CPU extra buffer types (`:1256`); the actual lab load used `CPU_Mapped` for experts. The mmap is `MAP_SHARED`, `PROT_READ` (`src/llama-mmap.cpp:488`, `:511`); CPU default buffers wrap mapped ranges (`src/llama-model.cpp:2035`). Tensor data is the mapped file offset, with no separate weight allocation (`src/llama-model-loader.cpp:1731`, `:1753`). This does not pin all experts.

The scheduler initially prefers the backend of each weight. For host weights assigned to the CPU, `op_offload` allows a higher-priority backend if it both supports and requests the op (`ggml/src/ggml-backend.cpp:1386`). CUDA accepts Q4_K `MUL_MAT`/`MUL_MAT_ID` (`ggml/src/ggml-cuda/ggml-cuda.cu:5970`, `:6011`). The threshold is read once from **existing runtime env** `GGML_OP_OFFLOAD_MIN_BATCH`, default **32** (`:182`), and stored in the CUDA device context (`:6579`, `:6602`). It is not a compile-time define.

CUDA's batch metric (`ggml-cuda.cu:6385`) is:

| Op | Metric used by CUDA offload request |
|---|---|
| `MUL_MAT_ID` | output `ne[2]`, i.e. **tokens in this ubatch**, not 8 routed experts or tokens per expert |
| `MUL_MAT` | output `ne[1]` |
| `GET_ROWS` | 0 (never at a positive threshold) |
| `ROPE` / `ROPE_BACK` | output `ne[2]` (scheduler excludes ROPE from weight-based placement at `ggml-backend.cpp:1373`) |
| Other supported ops | `ggml_nrows(op)`; this is not an expert-only knob |

The test is **>= threshold** (`ggml-cuda.cu:6400`). Consequently prompt ubatches >=32 can execute CPU-resident expert matmuls on CUDA. Short prompts and small final prompt chunks stay CPU. **Normal greedy one-token decode uses CPU expert matmuls** at default 32. Dense non-expert weights already on CUDA continue there with `--no-op-offload`. Flag wiring: `common/arg.cpp:2938`, `common/common.cpp:1754`, scheduler construction `src/llama-context.cpp:1435`. CLI documentation agrees: `tools/cli/README.md:63`, `:65`, `:78`.

Qwen35MoE creates down weights `[512,2048,256]` and gate/up `[2048,512,256]` for the supplied hyperparameters (`src/models/qwen35moe.cpp:57`, `:94`; J-OM14 stderr lines 45, 93, 116-117). Separate gate/up tensors are used when merged gate-up is absent (`src/llama-model.cpp:4091`). Graph: up, gate, down `MUL_MAT_ID` at `src/llama-graph.cpp:2462`, `:2475`, `:2587`; optional merged gate-up at `:2443` replaces the first two. The shared expert is a separate dense path, outside the routed expert override.

**Copies are selected, not unconditionally all 256.** The scheduler creates a destination with the **entire tensor layout**, not just selected experts (`ggml-backend.cpp:1794`, `:1799`), and creates new splits so offloaded weight storage can be reused (`:1751`). Inputs other than host weights are copied first; host weights last (`:2213`). The context always installs `sched_copy_experts` (`llama-context.cpp:1439`). If the split's first node is `MUL_MAT_ID` and its weight destination matches, it reads the router IDs back from GPU, synchronizes, builds the union of selected IDs, and groups consecutive IDs (`llama-context.cpp:3672`, `:3689`, `:3706`). Each group is uploaded using `ggml_backend_tensor_set_async` (`:3732`); CUDA issues `cudaMemcpyAsync(...HostToDevice...)` (`ggml-cuda.cu:2894`). Each group adds up to **512 bytes** after its last expert for MMQ padding, except at expert 255. Thus it may touch a small part of an unselected next expert.

For one layer/ubatch let S be the union across its top-8 router rows, E=|S| <= min(256,8N), and R(S) the number of consecutive ID runs. With separate up/gate/down, weight uploads are **3 R(S) logical async copies**, totaling `sum_t E*weight_t.nb[2] + <=3*512*R(S)` bytes. With merged gate-up they are 2 R(S). Using the supplied mixed-quant estimate, the primary bytes are about **E x 1.83 MiB per layer**. If all 256 appear, each tensor is one contiguous upload (~468 MiB/layer across three tensors); it is not 256 individual copies per tensor. GPU destination capacity remains full-sized even when E is small. Router copies, activation transfers, non-expert load copies, allocator work, warmup and driver behavior add to trace counts.

The selective callback is **conditional**, not a generic guarantee: if it cannot match the first node, it returns false (`llama-context.cpp:3673`, `:3677`), and the scheduler falls back to normal tensor copying (`ggml-backend.cpp:2128`, `:2135`). No MoE cache was requested (`llama-context.cpp:4951`); no permanent GPU cache avoids the next prompt's uploads. The provided trace alone cannot prove each split shape or assign all 10,645 H2D copies to experts. For normal routed splits the copy callback above is the concrete selected-copy path.

For CPU expert execution, the CPU implementation scans IDs into row lists (`ggml/src/ggml-cpu/ggml-cpu.c:1662`, `:1677`), skips unused experts (`:1691`), and reads `src0->data + expert*nb[2]` (`:1703`). It touches selected mmap pages. Activations and IDs cross backend split boundaries; no routed expert weight H2D is required for default one-token decode. The fill/pregate hook observes CPU `MUL_MAT_ID` nodes (`llama-context.cpp:1132`, `ggml-backend.cpp:2240`) and fills selected ranges before compute (`llama-context.cpp:1194`). Fill's configured max_tokens=1 limits this assistance to one-token ubatches (`:968`), so disabling prompt op offload does not turn on demand-fill for multi-token prefill.

**Decision levels:** knobs/placement are set before loading a run; graph allocation applies the configured size rule when transitioning between prefill/decode; selected-ID uploads and CPU page use happen within execution. Changing the wrapper between workloads is supported. An unchanged CPU decode placement does not imply unchanged decode time: prompt cache contents, allocator footprint, and numeric changes in the prompt's KV/recurrent state can carry over.

## Q2: UMA access and memory caching

[CUDA 12.6 Tegra memory management](https://docs.nvidia.com/cuda/archive/12.6.3/cuda-for-tegra-appnote/index.html#memory-management) states that these allocations share physical DRAM but have different access/cache behavior. For Orin (CC 8.7, I/O coherent), the relevant table is:

| Memory | CPU | Orin iGPU |
|---|---|---|
| Device (`cudaMalloc`) | no direct access | cached |
| Ordinary pageable malloc/file mmap | cached | no direct access in the 12.6 Tegra model |
| Pinned (`cudaMallocHost`) / registered host | CPU cached on CC >=7.2 | uncached |
| Managed allocation | cached | cached; driver coherence maintenance at launch/sync |

I/O coherence lets GPU reads see CPU cache updates; it is not full bidirectional cache coherence. The [current Tegra guide, sections 3.2 and 4.1](https://docs.nvidia.com/cuda/cuda-for-tegra-appnote/index.html#memory-selection), explicitly limits Tegra pageable GPU access / host-page-table access to Thor or later L4T hardware. Installing CUDA 12.6 does not give Orin HMM access to every Linux mmap. **Expected Orin attributes are an inference, pending the probe**, not values measured here. `integrated=1` or UVA alone does not establish this capability; `concurrentManagedAccess` describes managed memory, not arbitrary file pages.

There is a separate bounded registration option. [CUDA 12.6 `cudaHostRegister`](https://docs.nvidia.com/cuda/archive/12.6.3/cuda-runtime-api/group__CUDART__MEMORY.html#group__CUDART__MEMORY_1g46195a9f0702d6b021f423b0a47c800e) supports registering system allocations subject to device/OS support. Without host-page-table access, a CPU read-only mapping needs **`cudaHostRegisterReadOnly`**, whose support must be queried separately. `Mapped` plus `cudaHostGetDevicePointer` obtains a GPU alias even when host-pointer equality is unsupported. This pins physical pages on this platform; registration of an 18.3 GiB expert mapping cannot fit 7.4 GiB DRAM. It must be a bounded range/pool with explicit unregister and GPU completion before reuse. A successful registration can permit GPU reads without a weight memcpy, while its pin/fault cost and uncached access still matter.

`probe_uma.cu` maps **64 MiB of the actual model file `PROT_READ|MAP_SHARED`**; it never substitutes a writable anonymous mapping after failure. It prints all six requested attributes plus host-register and read-only support. It CPU-prefaults once, then checks equal checksums for device, registered file mapping (if permitted), cudaMallocHost, and direct pageable malloc (only if its attribute is 1). An unexpected pageable-capable platform also tests the unregistered file mapping. Setup includes allocation/initialization, or registration+alias; first/warm event times include only GPU reads. **Add setup to reads** when comparing total cost. This is a coalesced bandwidth probe, not an expert matmul or cold-NVMe benchmark. No CPU writes overlap GPU reads.

Pinned source already has a default-off `GGML_CUDA_REGISTER_HOST` helper (`ggml-cuda.cu:167`, `:5680`) using Portable|ReadOnly. Repository-wide call search found only definitions/declarations, no load-path caller. More fundamentally the CUDA backend supports CUDA device buffers, and CUDA_Host buffers on integrated GPUs, **not ordinary CPU_Mapped buffers** (`ggml-cuda.cu:6379`). Registering a pointer or exporting this env alone does not make the scheduler execute CPU_Mapped expert tensors in place. A zero-copy engine implementation would require the correct buffer representation and bounded pin lifetimes. Overriding all experts to CUDA_Host instead would allocate/load the entire expert set, which cannot fit.

## Q3: crossover prediction and discriminator

Checked `tests/test-backend-ops.cpp:13316`: its Qwen perf shapes are 128 experts, width 2048, FFN 768, and token sizes 1,4,8,32,64,128,256,512; it misses **2,16**, FFN 512 and 256 experts. More importantly `:1669`-`:1695` allocates and initializes tensors on the tested backend **before** timing at `:1748`. Its perf number excludes expert staging. Its `init_mul_mat_id_ids` at `:5671` shuffles a full expert list and slices the used IDs, so resident tests can also have realistic distribution. A custom test file could fix shapes but still would not include transfers. Therefore use the small external ggml harness, not a misleading resident-only `test-backend-ops perf -o MUL_MAT_ID` number.

`crossover.cpp` links the unchanged pinned ggml. Shapes: up/gate A=[2048,512,256], B=[2048,1,N]; down A=[512,2048,256], B=[512,8,N]; F32 activations, Q4_K weights, top-8 non-duplicate IDs/token. Seed-19 uniform routing, common prefix of 512 router rows; selected union and contiguous-copy count are reported. It measures exactly N=**1,2,4,8,16,32,64,128,512**, three repetitions/median each. All Q4_K projections are ~0.5625 MiB/expert (144 MiB/full tensor); two up/gate plus down =1.6875 MiB/expert. The actual UD-Q4_K_XL mix includes Q5_K/Q6_K, and the supplied aggregate is ~1.83 MiB/expert; this curve is specifically the requested Q4_K comparison, not a substitute for mixed-quant end-to-end timing.

`cpu_ms`: warm CPU op. `cpu_boundary_ms`: GPU activations+IDs readback, CPU op, GPU result upload. `gpu_resident_ms`: already staged GPU op. `gpu_staged_ms`: router readback+sync, union/grouping, pageable host uploads (same `nb[2]` and <=512-byte padding rule as engine), GPU op+sync. Activations already reside on GPU for both boundary paths. CPU/GPU outputs must have NMSE <5e-4 before timing is accepted. Resident quantized weights, allocations, tensor initialization, one warmup, result verification, and GPU context startup are outside timed iterations. Source weights are ordinary pageable CPU allocations, so CUDA's implicit staging/blocking is included. Storage faults, scheduler splitting, fused gate/up, complete 40-layer allocator behavior and steady page-cache competition are **not** modeled; runs 1,2,5,6 decide net value.

Prediction before GPU data: **N=1,2,4,8** favor/compete on CPU after staging; **16,32** are transition candidates; **64,128,512** increasingly amortize uploads and favor GPU if memory remains available. Confidence is low at small N on UMA because copies use DRAM bandwidth rather than a PCIe link. Weight bytes grow with selected union, not N alone (uniform expected union `256*(1-(248/256)^N)`); at large N they saturate. Per-expert mean work is `8N/256`, only 1 token/expert at N=32 on average. Do not import a discrete-GPU crossover number. A useful threshold must use **staged**, not resident, GPU time and leave N=1 decode on CPU.

[Fiddler v3](https://arxiv.org/html/2402.07033v3) motivates CPU for low expert token counts and GPU when reuse amortizes weight transfers; its uncompressed Mixtral/x86 results do not supply an Orin Q4_K crossover. [MoE-Infinity v3](https://arxiv.org/abs/2401.14361v3) motivates trace-aware expert caching from decode sparsity; it does not prove static hot-ID residency is beneficial in Satay's single RAM pool.

## Q4: placement limits and safe adaptation

Static `-ncmoe 39` with `-ngl 99` would place the last layer's entire expert tensors on GPU; **omit `-cmoe`** for that experiment. Static `-ot 'blk\.39\.ffn_(up|down|gate|gate_up)_exps=CUDA0'` can place that whole layer, provided the override precedes a broader matching CPU override. `-ot` cannot select expert ID 17 inside `[K,M,256]`. A whole layer costs ~468 MiB; four cost ~1.83 GiB. This budget is subtracted from the same RAM supporting the existing page cache, in addition to KV/recurrent buffers and scratch. Pinning hot file pages would retain one physical copy but also reduces reclaimability; copying to device can temporarily retain both file-cache and device copies. The correct discriminator is incremental avoided compute/I/O vs displaced page-cache misses on a held-out workload, not free "VRAM". No trace ranking was invented and no broad placement grid is proposed.

The one candidate's algorithm: default off returns `--op-offload`, threshold 32 without reading calibration. Opt in validates matching cold untraced p1 runs and decode/output consistency. Form the approximate three-projection cost `2*up_gate + down`; find the first N>=32 with >=10% staged GPU advantage at every larger sampled N. Before model load, if `MemAvailable < 4264 MiB` (2.5 GiB non-experts +537 MiB scratch +143 MiB KV/recurrent +1 GiB reserve), use `--no-op-offload`. Otherwise use CPU prompt if the real CPU-prefill measurement wins >=10%; if real GPU prefill wins >=10% and the curve has a crossover below this prompt's measured token count, select that threshold. Otherwise retain 32. The prompt is identified by SHA256 and the measured baseline token count (J-OM14's 195 tokens is replay context, not a new tokenization measurement). No character-count token estimate is used. This policy is scoped to p1/c4096/single greedy stream; recalibrate for another workload/image/thread setting. Low-memory choice is a conservative fallback, not a proof that a given allocation will succeed.

The existing batch-size rule already switches expert execution when a fresh prompt/decode graph is allocated. True mutable **within-execution** policy needs more work: threshold is a function-local static and then a device-context field; `op_offload` is supplied when creating the scheduler (`llama-context.cpp:1435`). Graph reuse at `:2367` skips rebuilding; new graphs reset/allocate at `:2382`, `:2397`. Changing placement must synchronize outstanding work, invalidate graph reuse/CUDA captures, rebuild copies/splits, and reserve buffers with correct ownership; the allocator already synchronizes changed assignments (`ggml-backend.cpp:2030`, `:2070`). There is no safe advertised live env switch. No new `LLAMA_EXPERT_*` name is introduced; strict validation at `src/llama-expert-fill.h:68` remains intact.
